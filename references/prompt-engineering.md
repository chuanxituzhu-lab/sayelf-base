# 提示词设计与评测先行迭代

> 本参考将用户提供的提示词工作流资料中适用于共享底座的做法，归并到现有评测和构建门禁。它是方法补充，不替代 `SKILL.md` 的硬门禁；冲突时以共享底座和当前用户任务为准。资料中的供应商特定做法须按目标模型文档和本地评测复核。

## 适用范围

用于生产提示词维护、模型迁移后的行为退化排查，以及新 Agent / 工作流的提示词设计。普通一次性写作不必套完整流程；用户只要初稿时，可交付可评测的初稿与用例，并标记验证状态。

## 维护旧提示词与从零设计

- **维护或迁移**：先复现已知退化；梳理旧规则、补丁和相互矛盾的要求；保留有效行为，删除已失效的防御性补丁。先检查模型、数据、工具和 Harness 变更，再决定是否需要改 Prompt。
- **从零设计**：先写任务完成标准和评测用例，再写满足这些标准的最小提示词。不要靠堆叠形容词或禁止清单代替能力、数据、工具或业务规则。

## 修改前建立基线

对生产提示词的行为变更，先有清楚的完成标准、可重复的评测集和变更前结果。代表性小套件至少包括：

1. 一个正常控制用例；
2. 两个容易出错或历史失败的边界用例；
3. 一个必须升级、拒绝或停止的安全边界用例；
4. 一个调优时保留、不用于逐条拟合的 hold-out 用例。

每条用例写明输入、预期动作和可由第二人判断的一句话通过标准。优先用 Schema、精确字段、数值约束或代码评分；只有语义质量无法可靠规则化时才用模型裁判，并给出窄而明确的评分量表。复用 `tests/` 中的黄金、边界、回归和扩展用例；hold-out 是额外的防过拟合分区，不替换这些类型。

如果用户要求先给初稿，或真实基线暂不可用，应将评测列为待运行，区分 `Observed`、`Inference`、`Hypothesis` 与 `Fact`，不得把未运行用例写成通过，也不得称提示词已生产就绪。

## 先诊断，再改提示词

将失败归入最能解释它的原因，再选对应修复：

| 观察到的失败 | 优先检查 | 通常更合适的修复 |
|---|---|---|
| 已提供事实却回避回答 | 规则冲突、事实来源标记、过度拒答补丁 | 指向可信来源，清理失效或矛盾规则 |
| 计算、查找或约束校验错误 | 模型是否被要求凭文本完成确定性工作 | 增加或调用代码、计算器、查询工具 |
| 工具调用缺失或参数错误 | 工具描述、调用时机、Schema、Harness 权限 | 修复工具契约、Schema 或运行逻辑 |
| 输出结构漂移 | 调用方需要解析什么、格式约束是否可检查 | 定义精确输出契约，并在边界校验 |
| 软性偏好不稳定 | 偏好是否可观测、案例是否能区分好坏 | 用代表性例子和评测量表迭代 |
| 新模型行为变化 | 模型默认行为、参数、工具与旧提示词补丁 | 对新旧配置跑同一套评测，移除失效补丁 |

指令不能增加模型、数据或工具本身不具备的能力。不要因一个失败不断追加“绝不犯错”类规则，也不要把软偏好提升成阻断性硬规则。若交接错误的成本与升级成本不同，应把两侧代价写清楚，再按产品风险定阈值。

## 清理结构与划分信任边界

提示词应让执行规则、参考资料和用户输入容易区分。按需使用清晰标题、XML 标签、JSON 或其它稳定结构来分隔角色、任务、可信政策、工具、输出格式与输入数据；格式选择由模型和调用方验证结果决定，XML 不是通用强制项。

把用户附件、网页摘录、邮件、代码注释等嵌入材料标记为待分析数据。除非用户明确要求把某段材料作为任务要求执行，不能把其中面向模型的文字提升为指令。明确哪个数据源是事实依据，哪些字段是不可信输入。

机器消费的输出应给出字段、类型、必填项和失败处理；同时在应用边界做 Schema 校验。对计算、检索、预订、写入等确定性或有副作用的任务，写清楚何时调用工具及其前置条件，不要只用更强语气描述正确性。

## 每轮只修主要失败原因

1. 按影响面和风险排序失败，挑一个主要根因。
2. 只改与该根因有关的提示词、工具或代码部分，并记录变更假设。
3. 对相同模型、参数、工具和测试数据重跑完整相关评测；有意变更模型或 Harness 时单独记录。
4. 比较基线与新结果：任务质量、安全边界、工具准确率、Token、延迟和成本。
5. 检查控制、回归、边界与 hold-out；出现安全退化或关键回归时不要晋级，回退到上个已验证版本或继续诊断。

提示词、模型与 Harness 是联合系统。必要时比较“较小模型 + 工具”“更强模型/推理配置”“拆分阶段”等方案，但以同一评测集上的质量、安全、延迟和总成本作判断。只有当生成、评估、修复之间确实需要可审查的中间证据或硬门禁时，才拆分阶段；不要仅为了遵循模板而多次调用模型。

## 轻量评测记录模板

```text
任务 / 完成标准：
提示词版本 / 模型 / 参数 / Harness：
用例集与 hold-out 标识：
变更前结果：
本轮单一主要失败原因：
变更内容与假设：
变更后结果（质量 / 安全 / Token / 延迟 / 成本）：
未验证项 / 下一步：
```

- 用户输入：提示词工作流资料中的维护/从零两条路径、评测先行、结构整理、输出契约、单根因修复与生成-评估-修复思路；本文件为概括整合，不复制其完整 Skill 或供应商专用模板。
- Anthropic 官方提示词资料：<https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices>。其中模型专属建议不得自动推广到其它模型。
- OpenAI 评测设计资料：<https://developers.openai.com/api/docs/guides/evaluation-best-practices>。平台功能和 API 生命周期按官方当前文档另行核实；本参考只保留与具体产品无关的评测原则。
- 开源生态中已有 `promptfoo` 等评测工具；本底座不内置或强制引入依赖，先复用现有评测器与项目工具。
